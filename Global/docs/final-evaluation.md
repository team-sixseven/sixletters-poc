# 기준 모델과 최종 평가

```text
개인 코드로 학습 → 검증 결과 비교·개선
                         ↓ 후보와 임계값 확정
                    final freeze
                         ↓ 저장한 모델로 예측
                  predict.py → final report
                         ↓
                    제출용 표·그래프
```

명령은 Docker 작업 환경을 켜 둔 상태에서 **Ubuntu 터미널의 저장소 폴더**에서 실행한다. 공통 데이터와 이름은 [README](../../README.md#2-music-준비와-사전-실습)에 따라 먼저 등록한다. **테스트는 팀이 방법·설정을 확정한 뒤 사용한다.**

## 1. 기준 모델 준비

임상 / ECG / 결합 입력마다 로지스틱 회귀(LR)와 랜덤 포레스트(RF)를 비교한다. 다음 명령은 등록한 이름 아래에 편집 가능한 개인 실험 6개를 만들며, 학습은 시작하지 않는다.

```sh
./dev baselines
```

생성 후 필요한 실험을 각각 실행한다. 팀원끼리 나누어 실행해도 공통 데이터·분할과 비교할 모델의 코드·설정은 같게 유지한다.

```sh
./dev exec baseline-lr-clinical train.py
./dev exec baseline-lr-ecg train.py
./dev exec baseline-lr-combined train.py
./dev exec baseline-rf-clinical train.py
./dev exec baseline-rf-ecg train.py
./dev exec baseline-rf-combined train.py
```

LR·RF 모두 학습 환자에서 결측치를 처리하고 범주형 변수를 변환하며, `class_weight="balanced"`로 적은 클래스에 더 큰 가중치를 준다. LR에는 표준화도 포함한다. 각 `train.py`·`config.toml`은 자유롭게 수정할 수 있다. 같은 이름의 실험이 있으면 `./dev baselines second`처럼 다른 접두사를 쓴다.

**입력 효과는 같은 모델의 3개 실행끼리** `./dev compare --mode inputs`로 확인한다. LR과 RF는 같은 입력 그룹끼리 `./dev compare`로 비교한다. 서버 결과는 `--remote`를 추가한다. [비교 조건](parallel-work.md#5-두-가지-비교를-구분하기)

## 2. 최종 후보와 임계값 고정

검증 결과·코드 리뷰로 제출 후보를 정한다. 필수 기준 모델과 채택한 개선 모델을 포함한다. 팀원들의 원격 후보는 먼저 각 원본 컴퓨터에서 [모델 보관](tracking.md#선택한-실행의-모델-보관)을 완료한다. 최종 평가할 컴퓨터에서도 같은 공통 데이터가 필요하다.

각 후보에서 저장된 모델을 불러오는 `predict.py`를 확인한다. 기본 예제는 전처리까지 포함된 `models/model.pkl`을 읽는다. 다른 모델 형식을 쓴 경우 읽기·예측 코드를 먼저 작성하고 검토한다. Pickle 모델은 읽을 때 코드가 실행될 수 있으므로 팀에서 출처·코드를 확인한 파일만 사용한다.

공용 MLflow의 후보를 선택하려면 다음을 실행한다. 보관한 모델·코드를 검증하여 내려받고, 선택한 실행을 고정한다. 기본 결과만 업로드한 후보는 사용할 수 없다.

```sh
./dev final freeze final-v1 --remote
```

목록에는 모델 보관이 완료된 실행만 표시된다. 고정할 번호를 공백으로 선택한다. `--owner 이름`·`--experiment 실험명`·`--dataset 데이터ID`·`--feature-set clinical`로 좁히고, `--list`로 선택 없이 조회한다. `--limit 50`은 표시 개수를 늘린다. 직접 고르려면 `--remote --run-ids MLFLOW_ID1 MLFLOW_ID2`를 사용한다. 번호 입력 중 `q`는 취소다.

로컬에 전체 실행이 있으면 `./dev final freeze final-v1`로 선택하거나 `--runs`로 직접 지정한다. `실행ID`는 결과 폴더 이름과 `result.json`의 `run_id`에 있는 **로컬 ID**다.

```sh
./dev final freeze final-v1 \
  --runs "Global/artifacts/작성자/실험명1/실행ID1" \
         "Global/artifacts/작성자/실험명2/실행ID2" \
  --reference 실행ID1
```

위 선택 방식은 대안이다. 같은 `final-v1`을 두 번 만들지 않는다. `--runs`와 원격 선택을 함께 사용하지 않는다. 모든 후보는 같은 공통 데이터·환자 분할·정답·검증 평가 기준을 사용해야 한다.

| 항목 | 고정되는 내용 |
|---|---|
| 후보 | 모델·코드·설정·검증 예측을 `Global/artifacts/final/final-v1/runs/`에 복사 |
| 임계값 | 예측 확률을 양성으로 판단하는 경계. 기본은 각 모델의 검증 예측에서 Youden J가 최대인 값 |
| 기준 모델 | `--reference`로 지정한 로컬 실행 ID. 생략하면 선택한 첫 실행 |
| 계획 | 데이터·분할·파일 식별 정보·평가 코드·패키지 버전을 `plan.json`에 기록 |
| 재현 허용오차 | 검증 확률의 작은 계산 차이를 허용하는 기준. 후보 확정 시 절대오차 `1e-7`·상대오차 `1e-5`를 함께 고정 |

Youden J는 **민감도 + 특이도 − 1**이며 동점이면 더 높은 임계값을 쓴다. 예측 확률이 임계값 이상이면 양성이다. 팀이 고정값을 미리 정했다면 freeze 명령에 `--threshold 0.5`처럼 0~1의 값을 붙인다. 이는 모든 후보에 같은 값으로 적용된다. 테스트 점수를 본 뒤 임계값을 고르지 않는다.

## 3. 저장한 모델로 최종 예측

고정 직후에는 후보별 준비 상태와 다음 명령이 표시된다. 이후에도 다음 명령으로 **완료·누락·오류를 한 번에** 확인한다.

```sh
./dev final status final-v1
```

보관한 표준 예측 코드와 현재 환경이 일치하면 바로 실행할 명령을 보여준다. 환경이 달라졌으면 새 실험으로 복원하는 명령을, 사용자 정의 모델은 모델 읽기 코드 확인 절차를 안내한다. 상태 조회는 학습·예측을 실행하거나 시험 점수를 표시하지 않는다.

예측 명령의 형태는 다음과 같다. `baseline-lr-clinical`은 예측 코드가 있는 실험명, `실행ID`는 계획에 포함된 **로컬 ID**다. `predict.py`는 모델을 다시 학습하지 않는다.

```sh
./dev exec baseline-lr-clinical predict.py \
  --plan Global/artifacts/final/final-v1 \
  --run-id 실행ID
```

**고정한 모든 후보에 대해 한 번씩 실행한다.** 표준 LR·RF 예제는 같은 `predict.py`로 읽을 수 있다. 다른 모델은 [restore](tracking.md#보관한-실험-복원)로 해당 코드·환경을 개인 실험에 준비한다. 다른 작성자의 개인 실험을 직접 실행하려면 파일명 앞에 `--owner "작성자"`를 붙인다. 기존 실험에 예측 파일이 없다면 `Global/templates/experiment/predict.py`를 개인 실험에 복사하고 모델 형식에 맞게 수정한다.

학습 이후 이름별 패키지가 변경되었다면 해당 실행을 `restore`한다. 보관된 패키지 파일이 있으면 그 버전의 분리 환경을 준비하므로 이름별 환경을 되돌릴 필요는 없다. 공통 환경으로 저장한 실행은 원본에 기록된 Python·패키지 버전과 현재 환경이 일치하는지 확인한다.

예측 코드는 계획에 보관된 모델로 검증·테스트 확률을 계산한다. 저장 시 검증 확률이 고정된 허용오차 안에서 재현되는지 확인한 뒤 테스트 예측을 기록한다. 환자별 차이는 `1e-7 + 1e-5 × |기존 확률|` 이하여야 한다. float32 연산의 미세한 차이를 허용하며, 기준을 넘으면 최대 차이·초과 건수를 표시하고 중단한다. 이때 모델·전처리·환경을 확인하고 **재학습으로 맞추지 않는다.** 허용오차와 실제 차이는 저장 기록에 남고 허용오차는 보고서의 `protocol.json`에도 포함된다. 이전 형식의 계획에는 기존의 더 엄격한 기준을 유지한다. 계획·모델·공통 데이터·평가 코드가 바뀌면 진행을 중단한다.

직접 작성한 예측 파일은 `FinalEvaluation(plan, run_id, data)`를 사용한다.

| API | 용도 |
|---|---|
| `run_directory` | 고정된 실행 사본. 이 안의 `models/`에서 모델 읽기 |
| `validation_data()` | 검증 입력. 기존 검증 확률 재현 확인에 사용 |
| `test_data()` | 정답을 제외한 테스트 입력 |
| `save(validation, test)` | 두 예측을 검사하고 테스트 예측을 한 번 저장 |

두 예측 모두 `patient_id`, `score` **순서의 두 열**로 전달한다. `score`는 양성 확률이며 모든 공통 환자를 한 번씩 포함한다. 정답 연결은 공통 기능이 담당한다. 전처리·모델의 `fit`은 호출하지 않는다.

## 4. 보고서 생성

모든 후보의 예측이 저장된 뒤 실행한다.

```sh
./dev final report final-v1
```

완료 경로는 `Global/artifacts/final/final-v1/report/`다.

| 파일 | 내용 |
|---|---|
| `metrics.csv`, `final_metrics.json` | AUROC·AP·Brier·민감도·특이도·정밀도·F1과 95% 신뢰구간, 혼동행렬 건수 |
| `deltas.csv` | 기준 모델 대비 점수 차이와 95% 신뢰구간 |
| `roc.png`, `pr.png` | ROC·정밀도-재현율 곡선 |
| `calibration.png`, `calibration.csv` | 예측 확률 구간별 실제 양성 비율. 5개 동일 너비 구간 |
| `confusion.png` | 후보별 혼동행렬 |
| `protocol.json` | 고정한 후보·임계값·데이터·평가 환경 |

신뢰구간은 기본 **2,000회, 시드 42**로 계산한다. 필요하면 최초 생성 명령에 `--repeats 5000 --seed 42`처럼 지정한다. 반복 수는 100~10,000이다. 환자를 복원 추출하며 같은 환자 표본으로 모든 모델을 평가하므로 모델 간 점수 차이도 짝을 맞춰 계산한다.

- **양성·음성 수를 유지하는 층화 bootstrap**이다. 관측된 클래스 수와 고정된 모델·임계값에 조건부인 구간이며, 재학습·모델 선택의 불확실성은 포함하지 않는다.
- AP는 scikit-learn의 [average precision](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html)이다. 사다리꼴 방식 PR 면적과 구분한다. 차이는 `후보 − 기준`이며 Brier는 음수, 나머지 지표는 양수일 때 개선 방향이다.
- 테스트가 한 클래스뿐이거나 지표의 분모가 0이면 해당 값은 `null`과 사유로 남긴다. `valid_resamples`는 유효한 재추출 횟수다. 사건이 적으면 신뢰구간이 불안정하거나 폭이 0일 수 있다.

보고서는 덮어쓰지 않는다. 테스트 결과를 본 뒤 다른 계획명으로 후보·임계값을 바꾸어 다시 선택하지 않는다. 이 절차는 통계적 평가를 남기는 기능이며, 임상 사용 가능성을 입증하지 않는다.

## 5. 제출 자료에 반영

`report/`의 집계표·그래프를 검토하고 [보고서 기준](../reports/README.md)에 맞게 `Global/reports/final/`로 복사한다. **상위 평가 폴더 전체를 복사하지 않는다.** `runs/`에는 모델과 검증 예측, `predictions/`에는 환자별 테스트 예측이 있다. 최종 평가 파일은 MLflow 자동 전송 대상이 아니다.

팀은 아래 내용을 함께 작성한다.

- 데이터 출처·정답·환자 포함/제외·결측치 처리·클래스 불균형
- 같은 환자의 임상 / ECG / 결합 비교, LR / RF 또는 gradient boosting 비교
- 검증 결과로 후보·임계값을 정한 이유와 최종 테스트 결과
- 오류 유형·주요 변수 해석·작은 사건 수와 데이터 범위의 한계

점수·그래프 자동 생성이 오류 분석이나 해석을 대신하지는 않는다. 사전 실습 결과와 최종 제출 모델의 결과도 구분한다.
